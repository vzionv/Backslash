# 性能与容量

## 已实施的优化

- PDF 预览从“全部页面立即渲染”改为当前页前后两页惰性渲染，DPR 上限为 2。
- 编译并发、等待队列、日志、项目、产物、任务历史和保留记录均有硬上限。
- POSIX 编译进程使用独立进程组；超时/取消终止进程树，避免残留 TeX 子进程。
- 数据库从 `sql.js` 整库内存快照迁移为原生 `better-sqlite3` + WAL；API key 使用计数 30 秒批量持久化。
- 构建日志写入数据库前截断，避免错误日志无限膨胀数据库和 API payload。
- 健康检查缓存磁盘/TeX 检测结果，不在每个请求遍历存储目录。
- 删除未被任何入口引用的 hooks、stores、旧查询封装和对应直接依赖。

## 容量模型

用户数不是主要指标，**同时编译数、同时保存频率、项目大小和 PDF 页数**才决定容量。

建议从以下保守配置开始：

```env
MAX_CONCURRENT_COMPILATIONS=2
MAX_QUEUED_COMPILATIONS=200
MAX_CONCURRENT_CLEAN_TASKS=2
SQLITE_BUSY_TIMEOUT_MS=5000
SQLITE_WAL_AUTOCHECKPOINT_PAGES=1000
BUILD_LOG_DB_MAX_BYTES=1048576
```

估算并发时，用真实最重项目测得单次编译峰值 RSS，预留 Web/WS/数据库和操作系统内存，再决定并发。例如单个 XeLaTeX 峰值 300 MiB 的机器，不能仅按 CPU 核数把并发设到几十。

## 发布前压测建议

依赖安装并成功构建后，至少执行三类场景：

1. **编辑保存**：50–200 个虚拟用户打开不同项目，每 2–10 秒保存一次，观察 p50/p95/p99、Web RSS、数据库大小和快照耗时。
2. **编译突发**：逐步增加并发提交，验证运行任务不超过上限、排队不超过上限、429 正确、取消/去重状态最终一致、超时后无孤儿进程。
3. **长文档浏览**：100/500/1000 页 PDF 连续滚动，观察浏览器 heap、canvas 数量、首屏时间和页面回收。

浏览器端应覆盖 Chromium、Firefox、Safari/Edge 中实际使用的平台；网络模拟至少包含 100 Mbps LAN 和高延迟/断线重连。

## 当前架构瓶颈

数据库已不再整库驻留内存或整库导出，但 `better-sqlite3` 仍是同步驱动，单个 Web 进程中的超大查询、无索引扫描或长事务会阻塞事件循环。当前容量上限主要来自：

- TeX 编译的 CPU 与峰值 RSS；
- 单 Web 进程承担 HTTP、文件操作、同步 SQLite 查询和编译调度；
- 同一项目的频繁保存、协作事件和 PDF 传输；
- Socket.IO presence/cursor/chat 状态保存在单个 WS 进程内存中。

支撑数百个账户不等于支撑数百个同时重编译的复杂项目。先用真实项目测量保存、列表、打开、编译和 PDF 浏览的 p95/p99，再按 CPU、内存和磁盘写入能力调整队列。需要多个 Web 写实例或多主机扩容时迁移 PostgreSQL；编译负载进一步增长时拆分为受限 worker，并使用共享任务队列。
